# PROJECT BRAHMA — EVENT CONTRACTS

> *"State represents truth. Events announce that truth has changed."*

**Project BRAHMA**
**Core Event Contracts**

---

# Purpose

This document defines the official **Event Contracts** of Project BRAHMA.

Event Contracts establish the architectural guarantees governing every event generated, published, transmitted, observed, and processed within the platform.

They provide a consistent, technology-independent mechanism for communication between loosely coupled engineering components.

---

# Scope

This document applies to every event generated by:

* Core
* Kernel
* Services
* Agents
* Workflows
* Memory
* Registries
* Providers
* Plugins
* Infrastructure
* Applications
* Future Engineering Components

---

# Why Events Exist

Modern engineering systems contain many independent components.

Direct communication between every component creates:

* tight coupling,
* circular dependencies,
* fragile architecture,
* poor scalability.

Events allow components to communicate without knowing about each other.

---

# Fundamental Principle

> **Events communicate that something has happened. They never instruct what should happen next.**

Events describe facts.

They never issue commands.

---

# Definition

An **Event** is an immutable notification that a state transition has already occurred.

An event answers one question:

> **"What happened?"**

It never answers:

* why,
* how,
* what should happen next.

Those concerns belong elsewhere.

---

# Event Philosophy

Project BRAHMA follows an event-driven architecture.

The architectural sequence is:

```text
State

↓

State Transition

↓

Event Created

↓

Event Published

↓

Subscribers React
```

State exists first.

Events exist because state changes.

---

# Events vs Commands

These concepts are fundamentally different.

| Event                      | Command                |
| -------------------------- | ---------------------- |
| Announces completed action | Requests future action |
| Describes the past         | Requests the future    |
| Immutable                  | May be rejected        |
| Broadcast                  | Directed               |
| Multiple listeners         | Single handler         |

Example

Good Event

```text
UserAuthenticated
```

Bad Event

```text
AuthenticateUser
```

---

# Events vs State

State represents current truth.

Events represent historical facts.

```text
Current State

↓

State Changes

↓

Historical Event
```

Events never replace state.

State never replaces events.

---

# Event Lifecycle

Every event follows the same lifecycle.

```text
Created

↓

Validated

↓

Published

↓

Observed

↓

Handled

↓

Completed

↓

Archived
```

Events never return to previous stages.

---

# Event Characteristics

Every Project BRAHMA event should be:

* Immutable
* Timestamped
* Identifiable
* Observable
* Serializable
* Technology Independent
* Self-Describing

---

# Event Identity

Every event must possess a unique identity.

Typical metadata:

* Event ID
* Event Name
* Timestamp
* Source
* Version
* Correlation ID
* Payload

Identity never changes.

---

# Event Naming

Events describe completed actions.

Good examples:

```text
MemoryCreated

AgentStarted

ProviderLoaded

WorkflowCompleted

SessionExpired

PluginRegistered

ConfigurationUpdated
```

Avoid:

```text
CreateMemory

StartAgent

RunWorkflow

LoadProvider
```

These are commands rather than events.

# Event Ownership

Every event has exactly one producer.

Multiple subscribers may observe the same event.

Example:

```text
Producer

↓

Event Bus

↓

Subscriber A

Subscriber B

Subscriber C
```

The producer never controls subscriber behavior.

---

# Event Bus

Events should travel through an Event Bus.

The Event Bus is responsible for:

* publication,
* routing,
* delivery,
* subscription management.

The Event Bus never performs business logic.

---

# Publisher Contract

Publishers guarantee:

* valid event,
* complete metadata,
* immutable payload,
* correct event type.

After publication, publishers relinquish ownership.

---

# Subscriber Contract

Subscribers guarantee:

* event validation,
* independent processing,
* failure isolation.

Subscribers must never assume execution order unless explicitly guaranteed.

---

# Event Payload

Every event may contain payload data.

Payload should contain only information required to understand the event.

Payload should avoid:

* internal implementation,
* private objects,
* executable logic.

---

# Event Ordering

Ordering guarantees depend on event category.

Possible ordering policies:

* Unordered
* FIFO
* Session Ordered
* Workflow Ordered

Ordering should be explicitly documented.

---

# Event Delivery

Project BRAHMA recognizes multiple delivery strategies.

## Synchronous

Publisher waits for completion.

---

## Asynchronous

Publisher continues immediately.

---

## Broadcast

Multiple subscribers receive the same event.

---

## Buffered

Events are temporarily stored before delivery.

---

# Event Immutability

Events become immutable immediately after publication.

Subscribers must never modify event content.

If new information is required:

Create a new event.

---

# Event Reliability

Delivery guarantees may include:

* Best Effort
* At Least Once
* Exactly Once (future)
* Configurable Policies

The guarantee should be documented by the implementation.

---

# Event Persistence

Not every event requires persistence.

Examples:

Persisted:

* WorkflowCompleted
* MemoryStored

Transient:

* CacheAccessed
* TemporaryNotification

Persistence policy belongs to infrastructure.

---

# Event Correlation

Complex workflows often generate multiple related events.

Correlation IDs connect related events.

Example:

```text
WorkflowStarted

↓

TaskCreated

↓

TaskCompleted

↓

WorkflowCompleted
```

All share one Correlation ID.

---

# Event Failure

If event processing fails:

* the event itself remains unchanged,
* subscribers handle failures independently,
* publishers remain unaffected unless explicitly configured.

Failure isolation preserves system stability.

---

# Event Dependencies

Events should depend only upon:

* Contracts
* Shared Event Definitions
* Core Types

Events must never depend upon:

* UI
* Applications
* Business Logic
* Concrete Implementations

---

# Architectural Guarantees

Every Event Contract guarantees:

* immutable identity,
* immutable payload,
* unique producer,
* observable lifecycle,
* technology independence,
* predictable metadata,
* loose coupling.

---

# Architectural Review Checklist

Before introducing an event:

✓ Does it describe a completed action?

✓ Is the name past-tense?

✓ Is the payload immutable?

✓ Is ownership defined?

✓ Is category correct?

✓ Is business logic absent?

✓ Is subscriber independence preserved?

Only then should the event be accepted.
